## Ownership and routes

Native Nest PayrollPoliciesModule exports PayrollPoliciesService.snapshotWithin(client,period,policyId?). Native PayrollCalculationsModule exports PayrollCalculationsService.calculateWithin(client,input). Both use existing injected database/auth/HTTP providers and the strict global Zod DTO pipe/OpenAPI. AppModule imports them. No dependencies or root/workspace build configuration are added. React policy feature uses RTK Query and existing reusable form controls, tabs and confirmation dialogs; browser packages remain independent.

GET /api/v1/payroll-policies?page=1 lists immutable versions and approval status; GET /payroll-policies/approvers?search=&page=1 looks up eligible named colleagues. POST /payroll-policies creates an inactive version; POST /payroll-policies/:id/approve requires a different active, live-linked HR manager and comment. Policy starts are first-of-month dates from 2000 through 9998. Finance/Director IDs are normalized UUIDs and must be active, non-system, live-linked salary readers (HR implicit rights); create, approve and snapshot access revalidate them. Policy identity/version/config/history cannot be updated or deleted. New changes require a new version and independent approval. The public version projection includes creation reason and named/role-labelled assignees, so reviewers see full saved settings rather than JSON or UUID forms.

Policy config has NO default statutory rates, caps, bases or applicability. HR explicitly selects rounding, monthly basic source (ledger or manual draft), per-component calendar/full-month proration, full-month ledger basis date (calendar period end or employment end), leave handling, PF/ESI enablement and employee/employer percentages, wage bases/caps/cap proration, optional eligibility ceilings and their full-month versus payable-earnings basis, PT state amounts or explicit manual input, TDS manual mode, Director requirement, assigned approvers and finalizerRole HR or FINANCE. Missing mandatory configuration fails validation. Employer contributions are explicitly separate from employee net deductions. Policy approval is authority for those supplied rules; the application does not assert legal/statutory correctness.

## Calculation contract and limits

POST /api/v1/payroll-calculations/preview requires authenticated HR, Origin and CSRF. Input: employeeId, period YYYY-MM, optional policyId (required if more than one current policy key applies), manualDraftId, expectedDraftVersion, pfEligible, esiEligible, stateCode, ptAmount, tdsAmount, leavingDate (explicit null if ongoing), unpaidDates (explicit empty array if none). It does not create a payroll run, finalize, pay, or modify the salary ledger. Other payroll capabilities consume calculateWithin inside their own authorized transaction.

Only approved effective policy versions and matching current India/INR manual drafts are accepted. No fallback to inactive, missing or superseded policy versions. Policy effective selection is at payroll month start, choosing the latest approved effective version per key; callers must select a key/version explicitly when ambiguous. Calendar months use actual calendar-day counts. Employee joining date comes from the database; leaving date and unpaid dates are explicit caller inputs because the employee schema has no leaving/attendance history. Unpaid dates must be unique and inside the month/employment overlap. Missing salary coverage, invalid leaving dates or non-INR consumed salary segments reject visibly rather than treating unknown pay as zero or introducing FX.

Authoritative uncorrected ledger tips split the payable employment span at effective changes. Pending/rejected requests and superseded salary rows do not supply compensation. Both ledger-based and manual-basic policies retain complete salary coverage/source fingerprints. Actual paidDays exclude unpaid dates; prorationDays may remain employmentDays when the approved policy chooses manual unpaid deduction. This prevents double charging: PRORATE_EARNINGS requires the manual unpaidLeave amount to be zero; MANUAL_DEDUCTION applies the manual amount once and does not also remove those days from earnings. Non-basic monthly components use the supplied manual draft amounts and explicit component proration mode. Full-month basis dates are consumed only when actually needed; an unrelated future non-INR rate does not invalidate a wholly manual basis.

Decimal arithmetic has precision 60. Money remains decimal text throughout transport, JSON and storage; only day counts use integer arithmetic. INR component/contribution rounding uses the policy-selected HALF_UP/FLOOR/CEIL at two decimal places. Earnings are rounded per component; gross sums those components, deductions sum their individually rounded values, and net is gross minus deductions. Negative net is rejected, not silently clamped. PF/ESI flags are supplied, never inferred; disabled-policy/eligible-flag conflicts and eligibility-ceiling conflicts reject. Ceiling comparisons explicitly choose full monthly component bases or payable earnings. Caps are explicitly full-cap or prorated by actual paid calendar days. Professional tax requires either a matching configured state rule or explicit manual amount; manual PT cannot be combined with state rules. Disabled PT/TDS requires zero explicit manual input. The approved policy explicitly replaces manual draft PF/ESI/PT/TDS fields with calculated/declared inputs; original draft values remain immutable evidence and the preview warns about replacement. No TDS slabs, PF/ESI statutory rates, tax exemptions, employer filing or other legal rules are invented.

The preview includes exact earnings, deductions, employer contributions, gross/deductionTotal/net; calendar/employment/paid/proration day counts; per-segment ledger IDs/correction IDs/amounts/currency/dates; normalized inputs; employee/manual-draft/policy versions and sourceHash/previewHash. Source fingerprints bind consumed ledger rows, employee version/joining date, the current immutable draft revision and policy/configuration. snapshotWithin uses the policy approval transaction advisory lock; calculator locks the subject employee and current draft header. Callers calculating multiple run lines must prelock all line employees in UUID order and retain the transaction through state change. Policy create/approve/snapshot use the same advisory key, preventing policy approval changes racing source validation. No preview is acceptance evidence or proof of 10k load capacity.
